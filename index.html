Composio AI Product Ops take-home

API access is common. Production readiness is the constraint.

I researched 100 requested apps to understand which ones could become useful agent tools today, which ones need Product Ops work, and what repeatedly gets in the way. I found that discovering an API is usually the easy part. Credential access, approval gates, incomplete event coverage, and the operational quality of the integration determine whether it is actually ready to ship.

What I found

The integration decision is operational, not binary.

01

Self-serve does not mean ready

Seventy apps provide free or trial access, but only 33 reached a ready-now verdict. Another 43 are technically buildable but still carry meaningful caveats around scopes, plans, events, or implementation quality.

02

The best route starts with existing leverage

Fifty apps already have a Composio toolkit. I would check the catalog first, verify that the required action exists, then use an official MCP, authenticated proxy, or new toolkit only when the existing path is insufficient.

03

MCP is a route, not proof of readiness

I found 12 official MCPs. An MCP can shorten integration work, but it does not remove the need to verify authentication, scopes, tool quality, reliability, and ownership.

Where I would focus first

Developer infrastructure and support have the clearest near-term wins.

Both categories contain six ready-now apps. Finance has no ready-now verdicts in this audit, while all ten productivity apps remain buildable with caveats. That suggests a portfolio strategy: ship repeatable, self-serve categories first, while routing commercial and approval-heavy integrations through Product Ops.

I measured the agent before trusting the output.

I froze the review sample before changing the prompt, then used the same 20 apps across both iterations. This kept the comparison stable.

I selected two apps from each category. One was the highest-risk record and one was chosen with a reproducible hash. A separate official-source review then checked ten material fields per app, giving me 200 comparisons.

The first pass mixed factual gaps with inconsistent labels such as “REST API” and “rest”. I therefore report both the raw exact-schema score and a conservative normalized baseline. I then constrained the taxonomy, required evidence for every material field, separated “not found” from “unknown”, and strengthened the checks for official MCPs and Composio coverage. On the identical frozen sample, exact agreement improved by 20.5 percentage points.

Authentication, MCP status, and buildability remained the weakest decisions. These are the fields I would route to Product Ops rather than treating the agent as final authority.

Where it improved

Structure made the research more reliable.

  • Canonical authentication and API vocabularies removed ambiguous labels.
  • Field-level evidence made unsupported conclusions visible.
  • Explicit unknowns reduced confident guesses when sources were incomplete.
  • Separate checks caught missed official MCPs and existing Composio toolkits.

What the final check means

The reviewed corrections were applied completely.

After I overlaid the reviewed records, the final 20-app sample matched the independent reference on all 200 fields. I use that as a correction-completeness check. It is not a claim that all 100 apps were manually verified.

The other 80 records are schema-validated, evidence-backed agent research. They should be refreshed as provider documentation, pricing, access rules, and MCP availability change.

Agent and workflow

I used the agent for breadth and humans for judgment.

The repository includes the research runner, the structured dataset, and a no-key validation mode so the work can be inspected without reproducing every model call.

  1. 01

    Research

    A Luna worker searched official developer, help, pricing, and source documentation for one app at a time.

  2. 02

    Structure

    Each answer was mapped to a fixed schema covering auth, access, API breadth, events, MCP, Composio coverage, buildability, blockers, and evidence.

  3. 03

    Validate

    The pipeline rejected incomplete records, invalid categories, unsupported enum values, missing evidence, and duplicate app IDs.

  4. 04

    Review

    A separate source review checked the frozen sample. I used the misses to improve the second pass, then applied the reviewed corrections.

What I would take forward

I would turn unsupported app requests into evidence-backed readiness decisions.

For each request, I would return the best route, the access path, the useful operations, the blocker, the confidence level, and the next owner. The outcome would be one of six paths: use an existing Composio toolkit, use a verified official MCP, use authenticated proxy execution for an uncovered endpoint, build a new toolkit, route access work to Product Ops, or defer when the evidence is insufficient.

This keeps the promise realistic. The value is not simply finding an API. It is creating a trustworthy path from user intent to an authorized, observable, repeatable external action.
